# 邀请增长机制实施方案

日期：2026-07-31  
状态：代码实施完成，待上线  
目标分支：`main`

## 1. 目标

把现有“全局固定比例、每笔充值即时返利”的功能升级为可配置、可审计、可退款冲正的一级邀请增长机制：

- 所有正常用户默认可邀请，不设置累计收益上限。
- 邀请人的比例由近 90 天有效付费邀请人数决定，档位替换而非叠加。
- 被邀请人仅在首笔真实支付成功时获得一次加赠。
- 邀请人返利先冻结 24 小时，降低退款和支付欺诈风险；被邀请人首充加赠立即可用，并在退款时冲正。
- 只做一级邀请，不形成多层现金分销关系。
- 保留现有用户专属比例作为管理员显式覆盖。
- 旧逻辑可回退，历史账本不重算、不篡改。

## 2. 默认业务规则

### 2.1 邀请人返利

| 近 90 天有效付费邀请人数 | 当前返利比例 |
| ---: | ---: |
| 0-2 | 8% |
| 3-9 | 10% |
| 10-24 | 12% |
| 25 及以上 | 15% |

达到 100 名等更高等级的合作方继续使用现有“用户专属返利比例”配置，由管理员审核后设置为 18%-20%。专属比例优先于自动档位。

### 2.2 被邀请人权益

- 首笔符合条件的真实支付充值加赠 5%，立即进入余额。
- 同一用户终身只获得一次首充加赠。
- 兑换码、管理员加款、补单、测试单和零金额订单不参与。
- 加赠与来源订单绑定，退款时按退款比例冲正。

### 2.3 有效付费邀请人定义

满足以下全部条件才计入当前档位：

1. 用户已绑定该邀请人，且不是自邀。
2. 在滚动 90 天窗口内至少有一笔已完成的真实支付订单。
3. 订单属于余额充值或订阅购买，支付金额大于零。
4. 订单未全额退款；部分退款后仍有正向净支付金额。
5. 每名被邀请人最多计数一次。

当前这笔真实支付会立即计入有效人数，因此第 3、10、25 名有效付费邀请人的订单会直接进入新档位。档位和比例按订单成功时的快照写入账本，以后变化不追溯重算历史奖励。

## 3. 兼容策略

新增 `affiliate_growth_mode`：

- `legacy`：保持现有固定全局比例行为。
- `tiered_v1`：启用本方案。

首次发布只增加能力，不自动切换生产配置。管理员确认后再将模式改为 `tiered_v1`。现有配置继续保留：

- `affiliate_enabled`
- `affiliate_rebate_rate`，仅供 `legacy` 使用
- `affiliate_rebate_freeze_hours`
- `affiliate_rebate_duration_days`
- `affiliate_rebate_per_invitee_cap`
- 用户专属 `aff_rebate_rate_percent`

在 `tiered_v1` 中，默认不限制单个被邀请人的累计返利；旧的单人上限只有大于零时才继续生效。

## 4. 配置模型

新增设置：

- `affiliate_growth_mode`，默认 `legacy`
- `affiliate_tier_window_days`，默认 `90`
- `affiliate_tier_rules`，默认 `[{0,8},{3,10},{10,12},{25,15}]`
- `affiliate_invitee_first_payment_bonus_rate`，默认 `5`
- `affiliate_effective_payment_min_amount`，默认 `0`，按实际支付金额判断

档位规则保存为结构化 JSON，读取时执行排序、去重、比例范围和首档阈值校验。解析失败时拒绝保存；运行时若发现历史脏配置则回退到内置默认值并记录告警。

## 5. 代码结构

### 5.1 规则层

新增独立的 `AffiliateGrowthPolicy`：

- 解析和校验档位配置。
- 计算有效邀请人数对应的比例。
- 判断订单是否符合真实支付、首充加赠和有效邀请条件。
- 生成不可变的奖励计算结果，不直接写数据库。

现有 `AffiliateService` 负责组织用户关系和调用规则层，不在支付回调中散落比例判断。

### 5.2 账本层

账本坚持 append-only：

- `accrue`：邀请人返利。
- `invitee_bonus`：被邀请人首充加赠。
- `rebate_reverse`：邀请人退款冲正。
- `invitee_bonus_reverse`：被邀请人加赠冲正。

每条记录保存来源订单、来源用户、规则模式、比例、档位人数和正负金额快照。来源订单与动作建立唯一约束，保证支付回调重放、任务重试和多实例并发不会重复发放或重复冲正。

### 5.3 资金一致性

- 奖励发放与账本写入在同一数据库事务中完成。
- 邀请人奖励优先进入冻结余额；成熟后沿用现有解冻流程。
- 被邀请人首充加赠直接进入余额，退款时按来源订单比例扣回；余额已被使用时允许形成负余额，由现有余额门禁阻止继续调用。
- 退款先冲减同一来源订单仍冻结的奖励，再冲减可用返利；已转入或消费的不足部分从邀请人账户余额扣回，允许形成负余额，由现有余额门禁阻止继续调用。
- 被邀请人加赠退款冲正与用户余额变更同事务执行；加赠已消费时同样允许形成负余额。
- 部分退款按 `累计退款金额 / 原订单金额` 计算累计应冲正额，再减去已冲正额，避免多次部分退款的浮点漂移。

## 6. 风控边界

- 禁止自邀和重复绑定。
- 真实支付订单才参与，兑换码不再触发 `tiered_v1` 奖励。
- 订单级唯一键防止 webhook 重放。
- 档位统计使用净支付订单，不按注册人数计算。
- 记录邀请关系、订单、IP/设备等证据，但第一期不做自动封禁；异常集中度进入管理端审计列表。
- 管理员专属比例修改只影响后续订单。

## 7. API 与界面

管理端设置新增：

- 模式切换。
- 90 天窗口和四档阈值/比例编辑。
- 被邀请人首充加赠比例。
- 冻结时长和旧的兼容配置。
- 保存前展示规则摘要和校验错误。

用户邀请页新增：

- 当前档位、当前比例。
- 距离下一档还差多少名有效付费邀请人。
- 被邀请人首充加赠说明。
- 冻结余额和预计可用时间保持现有展示。

中英文文案同步更新，禁止展示“比例叠加”或暗示多级返利。

## 8. 测试门禁

后端必须覆盖：

1. 档位边界 `0/2/3/9/10/24/25`。
2. 专属比例覆盖自动档位。
3. 首笔真实支付仅发放一次。
4. 兑换码、零金额、失败订单不参与。
5. 同一订单并发重放保持幂等。
6. 冻结、解冻、转余额与冲正。
7. 全额退款、两次部分退款和退款重试。
8. 90 天窗口边界与退款后的有效人数。
9. `legacy` 行为回归。

前端必须通过类型检查、单元测试和构建，并验证中英文、移动端和桌面端字段不溢出。

## 9. 上线顺序

1. 数据库迁移和后端能力上线，模式保持 `legacy`。
2. 管理端和用户端展示上线。
3. 对现有账本执行只读核对，不补发、不重算。
4. 在管理员后台保存默认档位，切换 `tiered_v1`。
5. 串行执行真实小额支付、首充加赠、重复回调、部分退款和全额退款验证。
6. 观察 24 小时后解冻、转余额和错误日志。

回滚只需将模式切回 `legacy`；已经写入的新账本保留审计，不删除、不反向篡改。

## 10. 实施拆分

- Phase A：规则对象、设置、档位统计和单元测试。
- Phase B：首充加赠、幂等账本、退款冲正和集成测试。
- Phase C：管理端和用户端界面、多语言、审计字段。
- Phase D：串行门禁测试、迁移审查和生产灰度方案。
